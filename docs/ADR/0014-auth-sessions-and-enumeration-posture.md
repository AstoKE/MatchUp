# ADR-0014 — Authentication sessions, email links and account-enumeration posture

**Status:** Accepted (Phase 1, 2026-10-24). §4 is amended by [ADR-0016](0016-auth-abuse-controls.md): sign-in timing and the reset cooldown also leak, and an Edge proxy is not recommended.

**Context.** Phase 1 had to deliver a secure auth foundation on three platforms using Supabase Auth, with Turkish-first UX and the guest-discovery decision (ADR-0013). Several choices were forced by what we observed against the real local stack rather than by documentation.

**Decisions.**
1. **Email + password, email confirmation mandatory, PKCE flow.** The server refuses sign-in for unverified accounts (`email_not_confirmed`), minimum password length 10 is enforced server-side (`weak_password`), refresh-token rotation on, JWT lifetime 1 h. Verified by integration tests, including: a PKCE code cannot be redeemed by another client, and codes are single-use.
2. **Session storage.** Native: encrypted at rest by the OS keystore via `expo-secure-store`, **chunked** (≈480 chars/item, count written last) because a session exceeds SecureStore's per-item limit; accessible `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`; corrupt/partial sessions are treated as signed out. Web: supabase-js default (`localStorage`) — a deliberate trade-off: XSS would expose it, so the web build must ship strict CSP/HTTPS headers (DEPLOYMENT, pre-pilot) and render user text as inert text only.
3. **Email-link landing is an allow-list, not a free-form redirect.** Links return to `/auth/callback`; the only supported `next` values are `/` and `/reset-password` (`sanitizeCallbackNext`). A separate `sanitizeReturnTo` (same-origin absolute paths only; never auth screens) governs post-sign-in navigation. Both are unit- and E2E-tested against open redirects. We do **not** depend on the `PASSWORD_RECOVERY` event for navigation: with PKCE it raced the callback screen and failed an E2E test.
4. **Account enumeration.** Sign-in (wrong password vs unknown email), password reset and unconfirmed-duplicate sign-up are indistinguishable (tested). **Residual risk, observed and pinned by a test:** the Auth API answers sign-up for an already-*confirmed* address with `422 user_already_exists`. The client treats it as success (so the UI shows no difference), but an attacker calling the API directly can probe addresses. Mitigations before public launch: CAPTCHA on sign-up (hosted Auth setting), IP/user rate limits at the CDN, and — if the risk is judged material — a thin Edge Function that fronts sign-up with a uniform response. Tracked as a Phase 7 hardening item.
5. **Server-authoritative account state.** `get_my_account()` returns status/verification/admin flags for UX; the database guard `private.assert_active_verified_user()` (used by every future write RPC) is what actually blocks unverified or suspended users.
6. **No custom `x-request-id` header.** Cross-origin custom headers force CORS preflights against the Supabase gateway and could silently break the web client; correlation uses Sentry breadcrumbs/tags instead.
7. **Sign-out is local-scope** (this device); the UI lands on the guest home page and the query cache is cleared on `SIGNED_OUT`.

**Consequences.** + Verified, tested auth with no known critical gaps. − Native paths (SecureStore on a real keystore, deep-link code exchange, `react-native-url-polyfill`) are covered only by unit tests with fakes and bundle compilation; they must be confirmed on a device in Phase 2. − Web session in `localStorage` raises the importance of CSP. − The enumeration signal above remains until a launch-time mitigation is chosen.
