# ADR-0017 — Account deletion and data export in SQL (no Edge Function)

**Status:** Accepted (Phase 2, 2026-10-25, founder approved). Amends DATABASE §11 and SECURITY §9; pulls F-29 from Phase 6 into Phase 2.

**Context.** DATABASE §11 planned deletion and export around Edge Functions holding the service-role key (purge: delete the auth user and storage objects; export: assemble JSON and hand out a signed URL). Measured on the local stack before building: the `postgres` role that owns our `SECURITY DEFINER` functions is **not** a superuser (as on hosted Supabase) but has `DELETE` on `auth.users`; `pg_cron` 1.6.4 is available; Supabase access tokens carry `amr: [{method, timestamp}]` for the sign-in and **a refresh keeps that timestamp**. There are no storage buckets yet (avatars were deferred).

**Decision.**
1. **Purge in SQL, scheduled with `pg_cron`.** `request_account_deletion()` → `PENDING_DELETION` (profile hidden, writes blocked by the existing guards) → 30-day grace, `cancel_account_deletion()` → daily `private.process_deletion_queue()` calls `private.purge_account()`: deletes sport profiles, settings and admin rows, turns the profile into a tombstone (`display_name`, bio, avatar, city, district cleared; `account_status = DELETED`), then deletes the `auth.users` row (sessions, identities, email). No service-role key exists anywhere in our code.
2. **Recent re-authentication from the token.** Requesting deletion needs a password sign-in within 10 minutes (`private.assert_recent_auth`, reading `amr`); otherwise `REAUTH_REQUIRED`. The app asks for the password and signs in again right before the request. Cancelling needs no re-authentication.
3. **Export is an RPC.** `export_my_data()` returns the caller's own data as JSON; the app saves it (web download, native share sheet). At most once per 24 h, serialized per user with an advisory lock. No signed URL is needed because nothing is stored server-side and the caller could already read most of it.
4. **Audit log in the `private` schema** (`private.audit_logs`): ids, a fixed action vocabulary and small metadata, no PII; append-only (UPDATE blocked by a trigger); not exposed through the Data API at all. Admin read access comes later through admin RPCs.
5. **Consent evidence stays** with the tombstone (version + time, no name or email) until counsel decides the retention (⚖).
6. **Inventory test.** A pgTAP test lists every `public` table with a `user_id` column or a foreign key to `profiles`; adding such a table (Phase 3+) fails it until export and purge handle the table.
7. Suspended accounts cannot self-delete for now (moderation evasion); their data requests go through support. Open question for counsel (⚖).

**Consequences.** + No privileged key or extra runtime; the whole lifecycle is tested with pgTAP and over real HTTP. + Re-authentication is verified by the server, not trusted from the client. − Storage cleanup is not covered: when avatars arrive, a small Edge Function (or Storage API call) must remove `avatars/{user_id}/…` during the purge. − Event-related effects (cancel organized future events, cancel participations as excused) do not exist yet; they are an obligation of the Phase 3 event engine and the inventory test will force the export/purge side. − A purged user's still-valid access token works until it expires (≤ 1 h) but maps to no account. − The "daily reconciliation" in DATABASE §11 (every non-deleted profile has an auth user) is not built yet.
