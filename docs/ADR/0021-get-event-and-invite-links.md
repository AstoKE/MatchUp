# ADR-0021 — `get_event` for the event page, and invite links as capability URLs

**Status:** Accepted (2026-10-30, completes Phase 3). Amends DATABASE §9 (`get_event`, `get_event_by_invite` become one function) and ADR-0020 decision 5 (invite-only events can now be requested).

**Context.** The event page read the `events` table and, with a session, `event_private_details`, through RLS. That could not show the organizer's name (profiles have no guest policy), a roster, or whether the viewer may open an invite-only event, and it exposed the organizer's user id to guests. Invite-only events existed in the data model (a 64-hex `invite_token`) but nothing could use them.

**Decisions.**
1. **One read RPC, `get_event(p_event_id, p_invite_token default null)`, open to guests** (the second function in the `anon` whitelist after `search_events`). It is `SECURITY DEFINER` and re-implements exactly the RLS visibility (a published public event for everybody; any status for the organizer and anyone with a participation row; admins), adds "the organizer's account is ACTIVE" for people not involved (as `search_events` does), and answers SQL `null` for anything the viewer may not see, indistinguishable from a missing event. The separate `get_event_by_invite` of DATABASE §9 is folded into the optional token argument.
2. **What it returns is decided per viewer on the server:** public fields (the organizer's user id is no longer sent; `is_organizer` is), the organizer's display name, the viewer's own participation status, private details (place, address, notes) and the roster of approved players' display names only for the organizer and `APPROVED` players, and the invite token only to the organizer of an invite-only event. Everyone else keeps seeing the counts. A pgTAP test pins the exact field list.
3. **Invite links are capability URLs:** `/e/<id>?invite=<token>`. Holding the link is the permission to see the event and to ask to join (the organizer still approves unless auto-approve is on). `request_join` takes the token as a fourth optional argument and answers `NOT_FOUND` without the right one (S-18); the old three-argument signature was replaced by the four-argument one with a default, so installed apps keep working. The token is never echoed to anybody but the organizer, never returned by search or listings, and not part of any notification payload.
4. **Not built, on purpose:** rotating or revoking a link. A leaked link stays valid until the event ends or is canceled; an organizer who regrets sharing can cancel and recreate, or remove people. A `rotate_invite_token` RPC is the obvious next step if the pilot shows links spreading.

**Consequences.** + One server-decided read for the page; no organizer id in guest responses. + Invite-only events work end to end. − A link in a URL can end up in browser history, a chat preview or a server log of whoever hosts the web build: the page shows a plain warning, the link is for people the organizer chooses, and analytics (Phase 7) must strip the query string. − `get_event` runs three small queries per page view; guest traffic to it is a scraping surface like `search_events` (page limits and the statement timeout apply; CDN rate limiting is a deployment item, SECURITY §3).
